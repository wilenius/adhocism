# Agent notes

This is a Hugo site whose content comes from a Logseq graph via the
`logseq-to-markdown` tool. GitHub Actions builds and deploys on push to `main`.

## Publishing flow

Use `just` — the `justfile` in this repo is the single entry point.

```
just            # list targets
just import     # export Logseq graph + sync into content/pages and static/logseq-assets
just build      # local Hugo build (validation; production deploy runs in CI on push)
just preview    # local Hugo dev server
just publish    # import + build + commit content changes + push
```

`just publish` is the full flow. It only stages `content/pages`, `content/tags`
and `static/logseq-assets`, so unrelated working-tree changes are left alone.

## Tags are pages, not taxonomy terms

`taxonomies` is deliberately empty in `config.yml`. A tag behaves the way it does
in Logseq: it is a page, it may carry its own prose, and everything referencing
it is listed underneath as "Linked references".

A tag pill resolves in two steps (`layouts/partials/tag_index.html`):

1. a Logseq page whose title is the tag (`en`, `fi`, `id`, `meta`) — prose and all
2. otherwise a stub under `content/tags/`

`scripts/generate_tag_pages.py` owns `content/tags/` entirely: it writes a stub
for every tag with no Logseq page behind it and prunes the rest. It runs from
`sync-exports.sh` *after* the rsync, and never from `content/pages` — that
directory is mirrored with `rsync --delete` and would eat the stubs. Stubs are
committed, because CI just runs `hugo` on committed content.

Tag pages sit outside `mainSections`, so they stay off the front page, the
archive, the RSS feed and the search index without needing a `hidden` flag.
`--check` reports drift without writing.

Adding a public Logseq page named after an existing tag is enough to upgrade it:
the generator drops its stub on the next sync and pills follow.

### Two bugs this replaced

**Pages silently missing from every listing.** Listings filtered on Hugo's
`Type`, but a Logseq page property named `type` lands in front matter and
overrides the section-derived value — `Co-crafting code (a research project)`
has `type: "project"` and vanished from the front page, the archive and every
backlink list. Filter on `Section`. `layouts/partials/listed_pages.html` is now
the single filter shared by the front page, the archive and the home RSS feed.

**Backlinks matching a bare filename.** `backlinks.html` appended the page's
base filename as a regex, so `id.md` matched any content containing "sidenotes",
"video", "consider" … Match the export's actual reference forms instead
(`ref "/pages/File"`, `#[Title](`, `\b`-anchored `#Title`), and regex-escape
every interpolated title — `Co-crafting code (a research project)` otherwise
becomes a pattern with capture groups.

## Configuration

The justfile reads two env vars with sensible defaults:

- `LOGSEQ_TO_MD_DIR` — path to the `logseq-to-markdown` checkout
  (default: `$HOME/git/logseq-to-markdown`)
- `LOGSEQ_GRAPH` — name of the Logseq graph to export
  (default: `hw-logseq`)

The export runs with `-o ./my-export -d -v -t`. The `./my-export` output
directory is not arbitrary: it is configured in Logseq to render only public
pages and blocks. Do not change it.

## Requirements

`just`, `hugo` (extended), `node`, plus a local clone of `logseq-to-markdown`
with its dependencies installed (`npm install` in that repo).

## PDF rendering via pandoc + tufte-handout

PDFs are generated by `render_pdf_from_markdown()` in `scripts/zenodo_export.py`
using `scripts/pandoc-template/sidenote.tex` and `note-filter.lua`.

### Known bugs fixed

**1. `-o -` (stdout) produced LaTeX, not a PDF.**
Pandoc infers output format from the filename extension. `-` has no extension so
pandoc emitted the intermediate LaTeX source. Fix: write to a temp `.pdf` file and
read it back.

**2. Blank line inside `\hypersetup{}`.**
When `author` is absent from the YAML header, the `$if(author)$...$endif$` block
expands to an empty line *inside* `\hypersetup{...}`. LaTeX keyval parsing can't
cross paragraph breaks. Fix: append `%` to each conditional line in the template so
the empty expansion becomes a LaTeX comment that eats the newline.

### Sidenote overflow: current status and known limitation

tufte-handout renders sidenotes via `\marginpar`. When more sidenotes are placed
than can fit in the margin, `\marginpar` squeezes them onto the current page and
clips any that overflow the bottom. **Overflow notes are silently dropped — they do
not defer to the next page.** `\clearpage` does not help; `\marginpar` overflow is
not a standard float queue.

Approaches tested and their outcomes:

| Approach | Outcome |
|---|---|
| `\usepackage{marginfix}` alone | "Too many unprocessed floats" — conflicts with tufte's internals |
| `\usepackage{morefloats}` + `\clearpage` | Still 1 page, overflow still dropped |
| `\usepackage{morefloats}` + `\usepackage{marginfix}` + `\clearpage` | No crash, still 1 page, overflow still dropped |
| Custom `\marginnote` with counter | Notes placed at anchor position; crowd/clip the same spot, overflow still lost |
| Dynamic text/margin ratio (current approach) | Best result so far — maximises notes visible on page 1 |

### Dynamic column width (implemented)

`_compute_layout_widths(post)` in `zenodo_export.py` estimates the ratio of main
text to footnote content (with a URL-density penalty) and computes `textwidth_mm` /
`marginwidth_mm` to balance the two columns. These are passed as pandoc YAML
variables and used in `\geometry{}` in the template.

Empirical results for "The three maxims of synthesised ethnography" (16 long citations):

| textwidth | citations visible |
|---|---|
| 130 mm (default) | 7 / 16 |
| 110 mm | 10 / 16 |
| 100 mm | 12 / 16 |
| 90 mm | 13 / 16 |
| 85 mm | 13 / 16 |
| 80 mm | ❌ crashes (`\MakeTextLowercase` error on long headings) |

**Minimum safe textwidth is 90 mm.** Narrower columns cause long section headings to
wrap in a way that triggers `\MakeTextLowercase has an extra }` during `\clearpage`.

The algorithm is clamped: `max(90, min(140, computed))`. For typical documents with
short or few footnotes, the default 130 mm is used. For note-heavy documents the
algorithm widens the margin automatically.

### Unresolved: the 3 missing citations

For very note-heavy documents the 3 remaining overflow citations still get dropped.
Ideas not yet tried:
- Replace the last N overflow notes with a "Notes" endnotes section via `endnotes` package
- Two-pass: first compile to find overflow log entries, second compile moves overflow to footnotes/endnotes
- Switch overflow notes to `paracol` or other two-column layout where flow is natural
- Just use `\footnote` (bottom-of-page) for all notes in the PDF — loses Tufte aesthetic but shows all content

## Tufte sidenotes: duplicated implementation

The site renders Tufte-style sidenotes (numbered, from Hugo footnotes) and
margin notes (from inline `[note: ...]` syntax) two different ways:

- **Live site:** `static/js/tufte.js` runs in the browser and rewrites the
  DOM at page load.
- **Zenodo export (HTML + PDF):** `scripts/tufte_transform.py` performs the
  same rewrite server-side, because WeasyPrint doesn't run JavaScript and
  Zenodo's HTML preview can't fetch `/js/tufte.js`.

If you change the note conventions (the `[note: ...]` syntax, the markup
emitted for sidenotes/margin notes, class names, counter behaviour, etc.)
you must update **both** files or the live site and the Zenodo artifacts
will drift apart.

The long-term fix is to move the transform into a Hugo render hook so
there is a single source of truth — that would let us delete `tufte.js`
and `tufte_transform.py` together. Until then, treat them as a pair.
