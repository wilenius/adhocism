+ I'm rewriting the Modular Moodle Plugin Development Assistant to be a proper agent skill with as deterministic workflows as possible. Current situation:

	+ Phase 1 (done): turned a pile of prompt docs into an agent skill

		+ The repo used to be .prompts/ — a folder of markdown files (core/, patterns/, plugins/) that the AI assistant scanned when writing Moodle plugin code (blocks, activities, filters, question types, etc.). That's all been deleted and replaced by skills/moodle-plugin-development/, a self-describing package that Claude Code or OpenCode can discover and load automatically, with progressive disclosure (load the base rules always, load a specific plugin-type contract only when needed). scripts/install_skill.py installs this skill into a target plugin project for either client.

	+ Phase 2 (ongoing, "Add public evaluation harness"): started building a way to test whether the skill actually works.

		+ This phase builds an eval/testing grader in the AI-tooling sense: automated checks that score whether an AI coding agent, given this skill, produced correct output.

		+ The idea, roughly:

			+ 1. evals/public/tasks.json — a list of realistic prompts ("replace this legacy filter with the modern namespaced filter class," "add a bulk action to the question bank," etc.), each tied to a starting fixture plugin (tiny skeleton plugins under skills/moodle-plugin-development/assets/fixtures/) and a target Moodle version.
			  2. tools/eval_harness.py — orchestrates the experiment: spins up an isolated copy of the fixture plugin, runs an AI client (OpenCode, or a "fake" client for testing the harness itself) against the task prompt under one of three conditions — candidate (this skill), released (a previously published version of the skill, for regression comparison), or none (no skill at all, baseline) — and records what it produced.
			  3. evals/public/graders.json + evals/public/graders/.../harness_contract_test.php — the actual pass/fail logic: deterministic checks like "does it install cleanly," "zero-warning Moodle coding-style CI," "does the PHPUnit test for the new filter class pass," "is output properly escaped." This is the "grader": a scorer, run in a disposable, network-isolated container so the AI being tested never sees the grading code or credentials (to prevent it from gaming the test).

	+ The eval harness's job is entirely about testing this skill's actual effect on real Moodle plugin code: it spins up real pinned Moodle checkouts (v4.5.13, v5.2.2), installs the AI-generated plugin changes into them, and runs Moodle's own tooling (Moodle Plugin CI, PHPUnit) as the objective judge.

	+ Only one of eight planned tasks has a working grader end-to-end, and it's only been proven with a "fake" client (no real model spend yet). The harness plumbing exists and is tested, but no real model has yet been fully evaluated through it.

	+ I'll be chipping away with this whenever I have spare tokens[note: I've been using OpenCode + GPT-5.6 Sol on xhigh thinking for this.]. It's quite token-intensive, so I expect it to take me maybe about a month before I have a release candidate?
